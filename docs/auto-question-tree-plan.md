# План построения дерева вопросов для подбора автомастерской

Дата: 25 октября 2026 года.

Источник услуг: [Иерархия автомобильных работ](auto-work-types.md).

## Цель и границы

Построить дерево, которое за минимальное количество понятных вопросов приводит от обращения владельца к услуге из справочника и требованиям к мастерской.

Дерево строится от понятных пользователю обращений к услугам. Механическое превращение разделов справочника в вопросы создаст длинную анкету, требующую знания автомобиля.

Пользователь может не знать деталей, путать термины, ошибаться и додумывать причину. Ответы нужно хранить как сообщения пользователя, а не как проверенные технические факты.

Конечный результат — конкретная известная работа либо подходящая диагностическая услуга. По симптомам нельзя обещать установление конкретной неисправной детали.

Этот документ — задание для следующего агента. Само дерево в рамках этого плана ещё не построено.

## 1. Подготовить каталог конечных результатов

Прочитать весь auto-work-types.md. Для каждой работы определить:

- устойчивый идентификатор;
- название из справочника;
- понятные бытовые названия;
- возможность выбора по словам пользователя либо необходимость предварительной диагностики;
- сведения, действительно необходимые для подбора мастерской;
- необходимые возможности исполнителя.

Различать два входа:

- Известная работа: «Хочу заменить свечи» → подбор исполнителя этой услуги.
- Жалоба: «Машина не заводится» → выбор подходящей диагностики. Жалоба сама по себе не означает необходимость замены свечей.

Результат этапа: каталог допустимых завершений разговора. Завершением может быть конкретная работа, диагностическая услуга или несколько сохраняющихся направлений.

## 2. Собрать обращения на языке владельца

Для всех разделов каталога составить примеры обращений, в которых пользователь:

- прямо называет услугу;
- описывает симптом;
- называет желаемый результат;
- описывает событие: ДТП, заправку, попадание воды;
- пересказывает чужое заключение;
- ошибочно называет предполагаемую причину;
- сообщает несколько проблем одновременно.

Например, «поменять аккумулятор» и «не заводится» могут пересекаться по исполнителям, но требуют разных путей уточнения.

Каталог описывает работы, но не содержит всех правил диагностики. Не достраивать из него неподтверждённые связи «симптом → сломанная деталь». Спорные связи отдельно помечать для проверки специалистом.

## 3. Определить слоты и условия их заполнения

Выделить общие слоты: цель обращения, известная услуга, основной симптом, текущее состояние, обстоятельства возникновения, предыдущая диагностика.

Добавить условные слоты для отдельных направлений. Например, тип коробки может понадобиться при обслуживании трансмиссии, но не при ремонте скола стекла.

Для каждого слота записать:

| Поле | Что требуется |
|---|---|
| Назначение | Как слот влияет на выбор услуги |
| Применимость | Когда его нужно заполнять |
| Значения | Включая неизвестное и противоречивое |
| Источник | Прямая фраза пользователя или вывод бота |
| Вопрос | Понятная формулировка для пользователя |
| Обязательность | Можно ли завершить подбор без него |

Незаполненный слот допустим. Обязательность определяется выбором услуги, а не желанием заполнить анкету.

Сохранять исходную формулировку, отличать наблюдение от предположения и результата предыдущей диагностики. Неизвестное значение не равно отрицательному; отсутствие упоминания симптома не означает его отсутствие.

## 4. Построить дерево от результата назад

Для каждой группы конечных результатов выяснить: какое минимальное различие нужно установить, чтобы выбрать между ними?

Из этих различий составить вопросы, затем объединить общие начала веток.

У каждого вопроса должны быть:

- условие появления;
- текст и варианты ответа;
- заполняемые слоты;
- переходы;
- объяснение, какое решение меняет ответ;
- путь для «не знаю» и свободного ответа;
- условие завершения.

Если все ответы ведут к одному результату и не меняют требования к исполнителю или необходимое ближайшее действие, вопрос удалить.

Технически допустим граф с общими узлами: повторяющийся вопрос не нужно копировать в несколько веток. Для пользователя он выглядит как последовательность вопросов. Предусмотреть вход с уже известными сведениями, чтобы не спрашивать повторно, а также обработку исправлений без полного перезапуска разговора.

## 5. Проверить каждый вопрос на доступность

Вопрос должен опираться на то, что человек мог заметить без специальных знаний.

Проверять:

- Поймёт ли вопрос человек, который редко водит?
- Может ли он ответить по памяти?
- Не заставляют ли варианты угадывать?
- Не содержит ли вопрос уже предполагаемый диагноз?
- Могут ли несколько вариантов быть верны одновременно?
- Изменится ли выбор мастерской при неточном ответе?

Предпочитать 2–5 вариантов, максимум 10. Число вариантов определяется содержанием. Разрешать свободный ответ и несколько вариантов, когда признаки могут сочетаться.

«Не знаю» не должно вести к повторению того же вопроса другими словами. Обычно оно ведёт к более широкой диагностике или другому доступному наблюдению.

Не предлагать запускать двигатель, разбирать автомобиль или выполнять опасные проверки ради заполнения слота. Короткие указания о ближайшем действии должны опираться на конкретные обстоятельства обращения.

## 6. Задать правила остановки

Завершать разговор, когда:

- известная услуга определена;
- выбрана достаточная диагностическая услуга;
- дальнейшие различия устанавливаются только осмотром;
- пользователь не знает деталей, а оставшиеся варианты может проверить один подходящий сервис.

Не продолжать вопросы ради определения конкретной детали.

В результате выдавать:

- выбранную услугу или сохраняющиеся направления;
- требования к мастерской;
- краткое описание жалобы;
- существенные неизвестные.

Количество вопросов минимизировать до достаточного выбора исполнителя, а не до доказанного диагноза. Если симптом исчез, сохранять и прошлое событие, и текущее состояние; исчезновение симптома не доказывает исправность автомобиля.

## 7. Проверить дерево сценариями

Сначала вручную пройти несколько разных направлений: запуск двигателя, тормоза, кузов, климат, электрика, известная услуга, установка оборудования. После исправления общих ошибок расширить покрытие на весь каталог.

Для каждой ветки проверить:

- точные ответы;
- бытовые и неточные формулировки;
- «не знаю»;
- ошибочное предположение о причине;
- противоречие или исправление предыдущего ответа;
- исчезнувший симптом;
- несколько жалоб.

### Обязательный сценарий: отказ после лужи

Реальный случай пользователя: после лужи машина потеряла тягу, заглохла при трогании, стартер крутил. Через 30 минут машина снова завелась. По сообщению пользователя, причиной были намокшие клеммы, которые затем высохли.

При проверке выдавать сведения постепенно, в ответ на вопросы. Будущий результат и причину не раскрывать боту заранее.

Ожидаемое поведение:

- короткий путь к подходящей диагностике;
- учёт изменения текущего состояния;
- отсутствие выдуманного диагноза;
- отсутствие серии вопросов о тонких различиях тяги, оборотов и ровности работы, если они не меняют маршрут.

Узнавать намокшие клеммы по исходным ответам дерево не обязано. Самостоятельно рекомендовать ожидание высыхания как универсальное решение нельзя выводить из этого единичного случая.

## 8. Оценить качество и сократить дерево

Проверять не только число вопросов, но и качество завершения:

- сколько вопросов потребовалось в каждом сценарии;
- какие вопросы не изменили результат;
- где пользователь вынужден угадывать;
- что происходит после «не знаю»;
- есть ли необоснованный переход к ремонту конкретной детали;
- все ли работы доступны через прямой запрос;
- все ли основные направления доступны через бытовое описание.

Не задавать одинаковую глубину всем веткам. Прямой запрос услуги иногда не требует уточнений; неоднозначная жалоба может потребовать нескольких.

Для каждого сценария явно записать ожидаемый результат, фактический путь и обоснование оставшихся вопросов. Не объявлять дерево оптимальным только на основании небольшой подборки примеров.

## Результаты работы следующего агента

1. Каталог результатов со связями на исходные работы.
2. Схема слотов с условиями применимости.
3. Дерево вопросов в читаемом виде и структурированном формате.
4. Таблица покрытия: работы справочника → возможные пути обращения.
5. Набор проверочных диалогов.
6. Список спорных переходов, которым нужна проверка автомобильным специалистом.

Начать с нескольких законченных веток и проверки на диалогах. Исправить принцип построения до распространения на весь справочник.
